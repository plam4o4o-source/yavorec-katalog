# Инвентар — десктоп приложение (Electron + SQLite)

Windows десктоп версия на библиотечния каталог, изградена с Electron и `better-sqlite3`.
Визуалният стил (хартиено-бронзова тема) е пренесен от оригиналното HTML приложение
`inventar-biblioteka.html`. Това е **отделен, самостоятелен проект** — не заменя
съществуващото HTML приложение и синхронизацията му с chyavorec.org.

## Структура на проекта

```
electron-app/
├── package.json          # зависимости, скриптове, electron-builder конфигурация
├── main.js               # главен процес — създава прозореца, инициализира SQLite, IPC handlers
├── preload.js             # безопасен мост (contextBridge) между интерфейса и main.js
├── icon.ico               # икона на приложението (Windows .exe и прозорец)
├── db/
│   └── schema.sql          # схема на базата данни + начални категории (изпълнява се при първо стартиране)
│   └── library.db          # SQLite базата данни (създава се автоматично, не се качва в git)
├── src/
│   ├── index.html           # разметка на интерфейса
│   ├── style.css            # стилове (хартиено-бронзова тема)
│   └── app.js                # рендиране на изгледите, форми, IPC заявки към main.js
└── .gitignore
```

При пакетиран (инсталиран) `.exe`, базата данни се създава в потребителската папка
на Windows (`%APPDATA%/Инвентар/library.db`), а не вътре в инсталационната папка на
програмата — така потребителските данни оцеляват при преинсталиране/ъпдейт.

## Инсталация (за разработка)

Изисква се [Node.js](https://nodejs.org) (LTS версия, 18+).

```bash
cd electron-app
npm install
```

`npm install` автоматично прекомпилира `better-sqlite3` за версията на Electron
(чрез скрипта `postinstall`). Ако видите грешка от рода „NODE_MODULE_VERSION“
при стартиране, изпълнете ръчно:

```bash
npx electron-rebuild -f -w better-sqlite3
```

## Стартиране (режим за разработка)

```bash
npm start
```

Отваря се прозорец 1280×800 (resizable). При първо стартиране `db/library.db`
се създава автоматично от `db/schema.sql`, с предварително заредени категории
(„книга“, „периодично издание“ и т.н.).

## Build на .exe за Windows

```bash
npm run build
```

Резултатът (`Inventar-Setup-<версия>.exe`) се появява в папка `dist/`, заедно
с `Inventar-Setup-<версия>.exe.blockmap` и `latest.yml` (нужни за автоматичното
обновяване — виж по-долу). Името на файла нарочно е на латиница — при кирилица
в името `latest.yml` сочи към различно име от реалния файл и автообновяването
не открива файла (проверено и поправено). Самата програма и прозорецът ѝ пак
се казват „Инвентар“ — засяга само името на инсталационния файл.
Конфигурацията е в `package.json` → `"build"` (electron-builder, таргет `nsis`).

- Ако правите build от Windows машина — работи директно.
- Ако правите build от Linux/Mac за Windows таргет, electron-builder изтегля
  необходимите Windows инструменти автоматично (изисква интернет при първия build),
  а за самия NSIS инсталатор е нужен и `wine` (пакети `wine64` + `wine32:i386`
  на Ubuntu/Debian) — без Windows това е единственият начин да се генерира
  пълноценно работещ `.exe` деинсталатор.

## Версии

Версията е във формàт **major.minor.patch** (напр. `1.2.3`) и се задава в
`package.json` → `"version"` преди всеки build (тя се вижда и в името на
инсталатора: `Inventar-Setup-1.2.3.exe`):

| Число | Кога се качва |
|---|---|
| **1-во (major)** | основни промени — нова архитектура, несъвместими промени в базата данни |
| **2-ро (minor)** | средни промени — нова функционалност, нов раздел, нова таблица |
| **3-то (patch)** | малки промени — поправка на бъг, дребна корекция в текст/изглед |

Версията и авторството се виждат автоматично в самата програма:
- долу вляво в страничното меню (под бутона „Служител“)
- в „Настройки“, най-долу на страницата

Текстът е: „Създадено от Пачо · Всички права запазени © &lt;година(и)&gt; · v&lt;версия&gt;“
— годината се изчислява автоматично (напр. „2026–2027“, ако програмата се ползва
и следващата година), версията идва директно от `package.json`, без да се пипа
ръчно другаде.

## Автоматично обновяване

Инсталираната програма проверява сама за нова версия в GitHub Releases на това
хранилище — при всяко стартиране, и по желание чрез бутона „Провери сега“ в
„Настройки“ → „Обновяване“. Ако намери по-нова версия, я изтегля тихо във фонов
режим; при затваряне на програмата (или чрез бутона „Инсталирай и рестартирай“)
новата версия се инсталира автоматично. Читателите/библиотекарят не правят нищо.

Това работи, защото хранилището `yavorec-katalog` е **публично** — изтеглянето
на release файловете не изисква никакъв токен или парола, вграден в програмата.
(Ако хранилището стане частно, автоматичното обновяване ще спре да работи, освен
ако не се добави GitHub токен в програмата — а това не е препоръчително, защото
всеки, инсталирал програмата, технически би могъл да го извлече от нея.)

### Автоматично publish чрез GitHub Actions (препоръчан начин)

`.github/workflows/release-electron.yml` build-ва инсталатора на истинска
Windows машина (GitHub-hosted runner — не е нужен `wine`) и публикува
GitHub Release с **и трите нужни файла** автоматично, веднага щом се качи таг
във формат `vX.Y.Z`:

1. Покачете версията в `electron-app/package.json` → `"version"` (вижте „Версии“ по-горе) и commit-нете
2. Създайте и push-нете таг със същата версия:
   ```bash
   git tag v1.2.0
   git push origin v1.2.0
   ```
3. Готово — GitHub Actions сам ще build-не `.exe`-то, `.blockmap`-а и `latest.yml`
   и ще ги публикува като Release (проверка: раздел „Actions“ в GitHub хранилището).

Workflow-ът може да се пусне и ръчно (без таг), от раздел „Actions“ →
„Build & publish Windows installer“ → „Run workflow“ (`workflow_dispatch`) —
удобно за тестов build без да се качва официална версия.

От този момент всяка вече инсталирана програма ще открие версията при следващото
си стартиране и ще се обнови сама.

### Ръчен build/публикуване (резервен вариант, ако Actions не е наличен)

1. Покачете версията в `electron-app/package.json` → `"version"`
2. Build:
   ```bash
   cd electron-app
   npm run build
   ```
   В `dist/` ще се появят **три** файла — всичките са нужни за обновяването:
   - `Inventar-Setup-X.Y.Z.exe` (самият инсталатор)
   - `Inventar-Setup-X.Y.Z.exe.blockmap`
   - `latest.yml` (описва на програмата коя е последната версия и къде да я вземе)
3. Създайте GitHub Release на адрес
   `https://github.com/plam4o4o-source/yavorec-katalog/releases/new`:
   - **Tag**: точно `vX.Y.Z` (напр. `v1.2.0`) — версията с малко „v“ отпред, задължително същата като в `package.json`
   - Провлачете (drag & drop) **и трите файла** от `dist/` в зоната за прикачени файлове
   - Оставете release-а **публикуван** (не „draft“ и не „pre-release“) — иначе програмите няма да го видят
   - Publish release

### Баркод четци (USB, без настройка)

Всеки USB баркод четец работи като клавиатура — въвежда сканирания текст и накрая
натиска Enter. Затова навсякъде в приложението, където се очаква сканиране, просто
е обикновено текстово поле, което слуша за Enter — не е нужна никаква настройка на
четеца или на приложението:

- **Заемане и връщане** — сканирайте читателската карта (полето разпознава точно
  съвпадение на № карта; докато пишете, се показват и живи предложения по име), после
  сканирайте баркода на всеки документ — заемането става веднага, с проверка за
  лимит книги на читател, вече зает документ, отчислен документ. За връщане —
  отделен таб със сканиране на баркода на върнатия документ.
- **Отчисляване** — сканирайте инвентарния номер на всеки документ, за да го добавите
  в списъка на акта.
- **Инвентаризация** — сканирайте инвентарните номера по време на проверка.
- **Баркод етикети** → „Проверка на четеца“ — пробен баркод „TEST-123“ за бърза
  проверка, че четецът е включен правилно (US клавиатурна подредба, добавя Enter).
- **Търсене** (книги, читатели) — сканирането в полето за търсене работи като обикновено
  въвеждане на текст.

### Печат — съвместимост с принтери

- **Обикновен принтер / A4** — всички документи (актове, протоколи, картони,
  инвентарна книга, КДБФ) и етикети във формат „A4 лист (3 колони)“ се печатат през
  стандартния диалог за печат на Windows; за PDF файл изберете „Microsoft Print to PDF“
  вместо физически принтер.
- **Ролкови лейбъл принтери** (Zebra, Brother QL, Dymo и др.) — в „Баркод етикети“ →
  „Формат на печат за етикети“ изберете „Ролков лейбъл принтер“ и въведете точната
  ширина/височина на етикета в мм; всеки етикет излиза на отделна „страница“ с точно
  този размер. В диалога за печат посочете лейбъл принтера като устройство.
- Форматът се пази в настройките и важи за всички следващи разпечатки на етикети
  (за фонда, за сигнатура, читателски карти), докато не го смените.

### Автоматизиран печат (документи и етикети)

Всички официални формуляри и етикети се печатат автоматично като готови документи
(през диалога за печат на Windows → „Microsoft Print to PDF“ за PDF файл), не само
като таблици на екрана:

- **Инвентарна книга** — пълна разпечатка по Приложение № 4 (пейзаж, чл. 26)
- **КДБФ** — трите части (Приложения № 1, 2 и 3) за избраната година
- **Акт за отчисляване**, **Акт за дарение**, **Протокол за придобиване без документ** —
  от съответния екран (Отчисляване / Постъпления), с текст по чл. 6, 30 – 39 и подписи
- **Заявка за МЗС** — от формата на съществуваща заявка
- **Читателски картон** — бутон „Картон“ в списъка с читатели, включва история на заемания
- **Напомнителни писма** — от „Просрочени“, групирани по читател, с изчислено обезщетение
- **Баркод етикети за фонда** — един етикет съдържа **името на библиотеката, баркод
  (Code 39) и инвентарния номер**; печат по диапазон или за целия фонд
- **Етикети за сигнатура** — отделен етикет за гръбчето на книгата: УДК, авторски
  знак, име на библиотеката, баркод и инвентарен номер
- **Читателски карти** — баркод карти за всички активни читатели
- **Дневник на библиотеката** — Раздел А и Раздел Б за избрания месец (пейзаж), с двата
  обобщителни реда „Всичко за месеца“ и „Всичко от началото на годината“

Форматът на етикетите (A4 лист с 3 колони или ролков лейбъл принтер с точен размер
в мм) се задава веднъж в „Баркод етикети“ → „Формат на печат“ и важи за всички
следващи разпечатки.

### Лев / евро

Всички суми в програмата се показват едновременно в лева и евро, по фиксирания
курс на въвеждане на еврото в България **1 EUR = 1.95583 BGN** (Регламент (ЕС)
2025/1409 на Съвета): картата на книгата, справките, КДБФ, актовете за
отчисляване/постъпление, напомнителните писма за просрочени — навсякъде.

При въвеждане/редакция на книга полето „Цена“ е разделено на **два отделни
входа** — „Цена (лв.)“ и „Цена (€)“. Въвеждате в кое да е от двете и другото се
преизчислява автоматично и веднага, докато пишете. В базата данни се пази само
стойността в лева (`books.price`); еврото винаги се извежда от нея по курса,
никога не се съхранява отделно.

### Цветови теми

„Настройки“ → най-долу — 6 готови цветови теми (Бронз по подразбиране, Наситено
синьо, Горско зелено, Бордо, Графит, Кафяво-теракота). Изборът се прилага веднага
и се пази в базата данни, така че важи за всички компютри, ако базата е споделена
(виж „Работа в локална мрежа“ по-долу).

### Работа в локална мрежа (споделена база данни)

„Настройки“ → „Работа в мрежа“ — базата данни (`library.db`) може да се премести
на споделена мрежова папка (мрежов диск), за да работят няколко работни компютъра
с един и същ фонд и читателски регистър едновременно. При избор на нова папка
програмата:

1. записва текущата база (WAL checkpoint + копиране на файла) в новата папка;
2. пази избора в отделен `config.json` в потребителската папка на Windows
   (`%APPDATA%/Инвентар/config.json`) — това е единственият начин програмата да
   „знае“ къде е базата, преди самата база да е отворена;
3. рестартира се автоматично, за да отвори базата от новото местоположение.

**Важно предупреждение** (показва се и в самия интерфейс): SQLite officially не
е проектиран за едновременен запис от няколко компютъра през мрежов дял (SMB) —
рискът от повреда на файла нараства, особено при нестабилна мрежова връзка. Това
е предвидената и заявена функционалност, но се препоръчва: (а) да се избягва
едновременен запис от двама души в един и същ момент, доколкото е възможно, и
(б) да се пазят редовни резервни копия на `library.db`. Бутонът „Върни към
локалното по подразбиране“ връща базата обратно на компютъра, без да губи данни.

**Намаляване на конфликтите при няколко компютъра:** когато е зададена
персонализирана (мрежова) папка, програмата автоматично:

- превключва от `journal_mode = WAL` на `journal_mode = DELETE` (rollback journal) —
  WAL разчита на споделена памет (mmap) между процесите, която не работи надеждно
  през мрежови файлови системи (SMB/CIFS), докато rollback journal е безопасният
  избор по документацията на SQLite за такъв случай;
- увеличава `busy_timeout` от 8 на 20 секунди — при опит за запис, докато друг
  компютър пише в същия момент, изчаква и опитва отново вместо веднага да
  гръмне с грешка „database is locked“.

Това намалява, но не премахва напълно риска — SQLite си остава файлова база
данни, а не истински клиент-сървър, затова горните препоръки (един по един,
редовни резервни копия) остават в сила.

### Служители

„Настройки“ → „Служители“ — списък със служителите на библиотеката, общ за
всички компютри, свързани към същата база данни. Всеки може да бъде добавен,
преименуван, деактивиран/активиран отново или изтрит (изтриването не пипа вече
записаните действия в одитната следа — те си остават с името, което е било
избрано към момента на действието).

Бутонът долу вляво в страничното меню („Служител: …“) отваря списъка с
активните служители — изборът кой точно работи в момента е **локален за
всеки компютър** (пази се в `config.json` на работната станция, не в
споделената база данни), точно както местоположението на базата данни. Избраното
име се записва автоматично в одитната следа при всяко действие (нов документ,
заемане, връщане, отчисляване и т.н.), без да е нужно да се въвежда всеки път.

### Автоматичен запис и резервни копия

Всяко действие (нов документ, редакция, заемане, връщане, отчисляване,
инвентаризация и т.н.) се записва **веднага** в базата данни — няма отделно
„незапазено“ състояние и няма нужда от бутон „Запази“ за самите данни (той
остава само там, където формата има много полета и логично изисква изрично
потвърждение, напр. основната форма в „Настройки“). Индикатор долу вляво в
страничното меню показва часа на последния запис.

„Настройки“ → „Резервно копие“:

- **Автоматично, веднъж на ден** — при първото стартиране на програмата за
  деня се прави копие на `library.db` в подпапка `backups` до базата данни
  (`auto-YYYY-MM-DD.db`); пазят се последните 30 дни, по-старите се трият сами.
- **Ръчно, по всяко време** — бутон „Направи резервно копие сега“ записва
  копие на избрано от вас място (полезно за USB/мрежов диск, за пренасяне на
  данните на друг компютър със същата програма).
- **Възстановяване** — от списъка с копия в „Настройки“ (бутон „Възстанови“),
  или чрез „Възстанови от файл…“ за копие отнякъде другаде (USB, друг
  компютър). Преди възстановяване текущата база автоматично се пази като
  допълнително копие (`before-restore-…`), за да не се губят данни при грешка;
  програмата се рестартира автоматично след възстановяване.

#### Криптиране на резервните копия

Ръчното копие може да се защити с парола (отметка в прозореца „Ръчно резервно
копие“). Използва се **AES-256-GCM**, а ключът се извежда от паролата чрез
`scrypt` със случайна сол за всеки файл; GCM дава и проверка за цялост, така че
подправен или повреден файл се засича при разшифроването, вместо да се
възстанови мълчаливо счупена база данни. Криптираните копия имат разширение
`.invbak` и се маркират с катинар в списъка; при възстановяване програмата сама
разпознава, че файлът е криптиран, и пита за паролата.

**Забравена парола = невъзстановимо копие** — няма резервен път за отключване.

Криптират се само **ръчните** копия — тези, които реално пътуват на USB или се
изпращат по интернет. Автоматичните дневни копия остават некриптирани, защото
лежат в подпапка до самата база данни, която също не е криптирана: парола там не
би добавила реална защита, а само риск от заключване на собствените ви данни.
(Ако компютърът трябва да е защитен и физически, това се решава с криптиране на
целия диск — BitLocker в Windows — а не на отделни файлове от програмата.)

### Ограничения на записите

„Настройки“ → „Ограничения на записите“ — горна граница за броя документи във
фонда и за броя читатели. **0 означава без ограничение** (по подразбиране).
Проверява се само при добавяне на нов запис; вече въведените данни остават
достъпни и редактируеми дори ако лимитът бъде намален по-късно. При достигане
на лимита добавянето се отказва с ясно съобщение, а в „Настройки“ се показва
лента за запълването (жълта при 85%, червена при 100%).

### Онлайн каталог през GitHub

„Настройки“ → „Онлайн каталог“ публикува `katalog.json` директно в GitHub
хранилището `yavorec-katalog`, откъдето сайтът chyavorec.org го чете на живо
през `raw.githubusercontent.com` (CORS-friendly, без нужда от сървър). Разлика
спрямо браузърната версия (`inventar-biblioteka.html`): тя нямаше достъп до
`git` от браузъра и разчиташе на отделен Windows Task Scheduler + `.bat` файл,
за да качва промените — тук Electron изпълнява `git` пряко, без нужда от
допълнителен скрипт.

**Еднократна настройка:**

1. На компютъра, на който е инсталирана програмата, направете `git clone` на
   хранилището веднъж (напр. `git clone https://github.com/plam4o4o-source/yavorec-katalog.git`)
   — изисква `git` да е инсталиран и вече удостоверен пред GitHub (Git
   Credential Manager, идващ по подразбиране с Git for Windows).
2. В „Настройки“ → „Онлайн каталог“ → „Избери папката на хранилището…“
   посочете получената папка.

**След това:**

- `katalog.json` се записва в тази папка автоматично при всяка промяна във
  фонда (нова книга, редакция, заемане, връщане, отчисляване).
- Програмата сама изпълнява `git add` / `git commit` / `git push` **на всеки
  5 минути**, ако има промяна — напълно автоматично, без ръчна намеса.
- Бутонът „Публикувай в GitHub сега“ прави същото веднага, без да чака
  таймера — полезно след важна промяна.
- Картата „Хранилище в GitHub“ пази потребител/хранилище/клон
  (`gh_user`/`gh_repo`/`gh_branch`, по подразбиране `plam4o4o-source` /
  `yavorec-katalog` / `main`) и сама сглобява публичния адрес
  `https://raw.githubusercontent.com/<потребител>/<хранилище>/<клон>/katalog.json`.

**Форматът на `katalog.json`** е `{library, place, generated, items: [...]}` с кратки
имена на полетата (`inv, a, t, s, c, p, y, v, l, u, g, o, k, n, cv, av`) — нарочно
**идентичен** с формàта, който `inventar-biblioteka.html` и страницата на сайта вече
очакват, за да могат да се използват взаимозаменяемо без промяна на сайта.

**Предпазна мярка:** ако фондът в текущата база данни излезе празен (напр. прясна
инсталация, към която по грешка е свързана папка с вече публикуван непразен каталог),
програмата **отказва** да презапише непразен `katalog.json` с празен — както при
автоматичния запис, така и при ръчните бутони. За наистина умишлено изпразване на
публичния каталог използвайте „Ръчен експорт“ вместо автоматичното публикуване.

### Дневник на библиотеката

Електронен вариант на официалния месечен статистически дневник на читалищните
библиотеки, по образец на `e_Dnevnik_AB_CH2` — един ред на календарен ден, с два
раздела (превключват се с таб в горната част на екрана, тъй като заедно имат над
70 колони):

- **Раздел А** — часове на обслужване, всички записани читатели с разбивка по
  възраст, пол, образование, професия и учащи се, и всички посещения (в заемна
  за дома, деца до 14 г., в читалня, интернет).
- **Раздел Б** — часове на обслужване и всички заети книги/периодични издания/
  други материали с разбивка по вид, език и съдържание (класификация по УДК).

**Попълва се направо в таблицата** — всяка клетка е поле за въвеждане, както в
хартиения дневник; стойността се записва веднага при излизане от полето (кратко
зелено премигване потвърждава записа) и обобщителните редове се преизчисляват на
момента, без пречертаване на цялата таблица, за да не се губи мястото, докъдето
сте стигнали. Бутонът „Подробно за днес…“ отваря същия ден в разгъната форма,
групирана по раздели, ако е по-удобно да се попълва така.

Часовете на обслужване се въвеждат във формат **чч:мм** и се сумират правилно
като продължителност (не като обикновено число). Нито едно поле не е
задължително — попълва се наличната информация за деня.

Записът на клетка от единия раздел изпраща и стойностите на другия, защото редът
в базата се презаписва изцяло — иначе попълването на Раздел А би нулирало вече
въведения Раздел Б за същия ден.

Редовете „Всичко за месеца“ и „Всичко от началото на годината“ **не се пазят
отделно** — смятат се живо от вече записаните дни при всяко отваряне на
раздела, така че винаги остават верни, без ръчно пресмятане. Печатът възпроизвежда
и двата обобщителни реда; експортът в CSV извежда суровите дневни данни в
отделни колони.

## Схема на базата данни

```sql
categories(id, name)
books(id, inv_number, barcode, register_date, title, subtitle, author, category_id -> categories,
      year, volume, isbn, pages, language, udk, call_number, author_mark, city, publisher,
      keywords, annotation, cover_url, department, status, price, description,
      acquisition_id -> acquisitions, deaccession_act_id -> deaccession_acts, deaccession_date, created_at)
inventory(id, book_id -> books, quantity)
inventory_checks(id, book_id -> books, date)
acquisitions(id, no, year, date, how, from_source, doc_type, doc_no, doc_date, total_count, sum, donor_address, note)
deaccession_acts(id, no, year, date, order_no, reason_code, reason_text, disposal, attach, committee1..3)
deaccession_items(id, act_id -> deaccession_acts, book_id, inv_number, author, title, volume, year, price, udk, category, language)
inventory_sessions(id, date, scope, department, committee1..3, pool_size, closed)
inventory_session_scans(id, session_id -> inventory_sessions, book_id, scanned_at)
inventory_session_missing(id, session_id -> inventory_sessions, book_id, inv_number, title, author, price)
readers(id, name, phone, address, address2, email, card_no, egn, id_card_no, id_card_date, id_card_issuer,
        birth_date, category, registered_at, re_registered_at, status, gdpr_consent, parent_consent, note, created_at)
loans(id, reader_id -> readers, book_id -> books, date_out, date_due, date_in, fine)
periodicals(id, title, freq, publisher, issn, department, note)
periodical_issues(id, periodical_id -> periodicals, issue_no, date, price, note)
mzs_requests(id, no, year, date, direction, partner, author, title, isbn, requester, status, due_date, note)
audit_log(id, ts, user, action, detail)
visits(id, date, count)
employees(id, name, active, created_at)
dnevnik_days(id, date, a_hours, a_age_u14..a_visit_internet — Раздел А, b_hours, b_type_books..b_cat_reading_used — Раздел Б, note)

         loan_days, max_books, extensions_count, extension_days, fine_per_day, annual_fee,
         free_access_pct, next_inv_number, committee1..3, lbl_mode, lbl_w, lbl_h, theme, catalog_folder,
```

`date_in IS NULL` в `loans` означава, че заемането е активно (книгата все още е заета).
`status = 'отчислен'` в `books` означава, че документът е изваден от фонда с акт и не се брои в наличностите/статистиката.

## Как да добавя нова таблица

1. **Схема** — добавете `CREATE TABLE IF NOT EXISTS ...` в `db/schema.sql`.
   Схемата се изпълнява при всяко стартиране (`CREATE TABLE IF NOT EXISTS` не
   пипа съществуващи таблици), така че промяната важи веднага за нови инсталации.
   За съществуваща база с вече записани данни добавете отделен `ALTER TABLE`
   блок, обвит в проверка (напр. `PRAGMA table_info` или `try/catch`), защото
   SQLite не поддържа `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`.

2. **IPC handlers** (`main.js`) — добавете `ipcMain.handle('таблица:действие', ...)`
   по образец на съществуващите (`books:list`, `books:create` и т.н.). Използвайте
   помощната функция `run(fn)` — тя хваща грешки и връща `{ok:false, error}`
   вместо да чупи приложението.

3. **preload.js** — изложете новите канали през `contextBridge`:
   ```js
   mytable: {
     list: invoke('mytable:list'),
     create: invoke('mytable:create')
   }
   ```

4. **app.js** — добавете нов запис в `NAV`/`TITLES`, функция `renderMyTable()`
   в обекта `renderers` в `route()`, и форма по образец на `bookForm`/`readerForm`.

## Как да добавя ново поле към книга (пример)

1. `db/schema.sql`: добавете колоната в `CREATE TABLE books (...)`.
2. `main.js`: добавете полето в `BOOK_SELECT`, `books:create` и `books:update`.
3. `src/app.js`: добавете `<input name="ново_поле">` в `bookForm()` и полето
   в `payload` в `saveBook()`.

## Забележка за обхвата на тази версия

Тази Electron версия пренася всички модули на `inventar-biblioteka.html`,
включително публикуването на онлайн каталога към chyavorec.org — но по
по-прост начин, тъй като Electron (за разлика от браузъра) може да изпълнява
`git` пряко: не е нужен отделен Windows Task Scheduler + `.bat` файл, каквито
изискваше браузърната версия (виж „Онлайн каталог през GitHub“ по-долу).

Не пренесени (защото са специфични за браузърната архитектура на другото
приложение, не за самата библиотечна дейност): криптиране на файла на диска,
File System Access API избор на папка, ротационни резервни копия в браузъра.
Печатът на официалните документи и етикети, шестте цветови теми, работата в
локална мрежа и автоматичното публикуване на онлайн каталога (виж съответните
раздели по-горе) вече са включени. Ако друго конкретно нещо ви трябва, кажете кое.
