# Как се предлагат промени

InvLib е безплатна библиотечна система за читалищни, училищни, общински и
обществени библиотеки. Води регистрите по **Наредба № 3 от 18.11.2014 г.** —
инвентарна книга, КДБФ, дневник, актове за отчисляване, протоколи от
инвентаризация — и работи офлайн, на един компютър с Windows, без абонамент.

Проектът е поддържан основно от един разработчик за нуждите на конкретно
читалище, но следва обичайните практики за отворен код, за да е лесно за
преглед, независимо кой прави промяната (човек или AI асистент).

> **In English:** [`CONTRIBUTING.md`](CONTRIBUTING.md) — същият документ, същите
> правила.

Не е нужно да сте опитен програмист, за да помогнете. Ясно описан проблем или
разказ как се е държала програмата във вашата библиотека също е принос — вижте
[Доклад за грешка](#доклад-за-грешка) и
[Обратна връзка от библиотека](#обратна-връзка-от-библиотека).

### 1. Разклоняване (fork)

Отворете <https://github.com/plam4o4o-source/yavorec-katalog> и натиснете
**Fork** горе вдясно. Получавате собствено копие, което можете да променяте
свободно.

### 2. Клониране

Заменете `<вашето-име>` с потребителското си име в GitHub:

```bash
git clone https://github.com/<вашето-име>/yavorec-katalog.git
cd yavorec-katalog
```

### 3. Клон за промяната

Никога не работете направо в `main`. Името на клона да казва каква е промяната:

```bash
git checkout -b feature/istoriya-na-zaemaniyata
```

Представки: `feature/` за нова възможност, `fix/` за поправка, `docs/` за
документация.

### 4. Зависимости

**Програмата е в папка `electron-app/` — в корена на хранилището НЯМА
`package.json`.** Всички команди по-долу се изпълняват оттам:

```bash
cd electron-app
npm install
```

`npm install` пуска стъпка `postinstall` (`electron-rebuild`), която компилира
`better-sqlite3` за ABI-то на Electron — това е нужно на пакетираната програма.

**Тестовете обаче вървят на обикновен Node**, затова веднага след инсталирането
този модул се компилира обратно:

```bash
npm rebuild better-sqlite3
```

Без тази стъпка `npm test` пада с `NODE_MODULE_VERSION mismatch` на чист клон.
Не е грешка във вашата настройка — CI прави същите две стъпки
(`.github/workflows/ci.yml`).

Пускане на самата програма при разработка:

```bash
npm start
```

### 5. Тестове

Ползва се вграденият в Node `node:test`; няма външна тестова рамка.

```bash
npm test
```

Към момента това са **1900+ теста** и отнема няколко минути. Пуснете ги веднъж,
преди да пипате каквото и да е, за да видите изходното зелено състояние.

CI пуска поредицата **два пъти**, в две часови зони, защото няколко теста за
лятното часово време имат разграничителна сила само извън UTC. Пуснете и
второто минаване, преди да отворите pull request:

```bash
TZ=Europe/Sofia npm test
```

Публичната каталожна страница има две отделни поредици, които са извън
`electron-app/` и затова не се хващат от `npm test` — едната проверява как
каталогът СТИГА до страницата (източници, срокове, кеш), другата какво прави
страницата с него при реален мащаб от 15 000 екземпляра:

```bash
cd ../site
NODE_PATH=../electron-app/node_modules node test-page-katalog.js page-katalog.html
NODE_PATH=../electron-app/node_modules node test-page-katalog-view.js
```

Първата трае към минута и изглежда заседнала: изчаква истинските производствени
срокове на страницата (6 сек. за заглавките, 25 сек. за тялото, за всеки
източник). Това чакане Е самата проверка.

И четирите проверки — двете часови зони и двете за каталожната страница — с една
команда:

```bash
npm run test:all
```

**Нова функционалност или поправка без нов/обновен тест не се приема.**
Правилото е файл на всеки handler — `handlers/x.js` → `test/handlers-x.test.js`
— с фалшив `ipcMain` и **истинска** временна база (`fs.mkdtempSync` +
`db/schema.sql`). Самият SQL не се мокне: базата е точно това, което си струва
да се тества.

### 6. Описване на промяната

Всяка смислена промяна (нов домейн, поправка на бъг, ново поле) получава:

1. **Вдигане на версията** в `electron-app/package.json` **и**
   `electron-app/package-lock.json`. И двете — сверяват се едно срещу друго.
2. **Запис в `electron-app/CHANGELOG.md`**, двуезичен (BG/EN): какво се променя,
   *защо*, и брой тестове преди/след. Официалният сайт чете този файл, тоест
   записът се публикува такъв, какъвто е написан.
3. **Един commit за една промяна.** Несвързани неща вървят в отделни commit-и,
   дори да са открити в едно и също разследване.

Според това какво сте пипнали, обновете и:

| Какво сте променили | Какво да обновите |
|---|---|
| Поведение, което библиотекарката ще забележи | `docs/narachnik.html` (наръчникът) |
| Нова таблица или колона | `docs/ARCHITECTURE.md`, коментарите в `db/schema.sql` |
| Нещо по Наредба № 3 | `docs/naredba-3-karta.md` |
| Настройки или build | `electron-app/README.md` |
| Екранът | Снимка в `docs/screenshots/`, ако старата вече не отговаря |

Записвайте разсъжденията, не само промяната. Този код обяснява **защо** съществува
даден ред — точно това прави откритият след две години дефект разбираем, вместо
загадъчен.

### 7. Pull request

```bash
git push -u origin feature/istoriya-na-zaemaniyata
```

Преди това проверете:

- [ ] `npm test` минава, и `TZ=Europe/Sofia npm test` също
- [ ] нов или обновен тест покрива промяната
- [ ] версията е вдигната в `package.json` **и** в `package-lock.json`
- [ ] `CHANGELOG.md` има двуезичен запис
- [ ] pull request-ът съдържа една смислена промяна, не няколко несвързани
- [ ] няма нова зависимост без обосновка в описанието

Хранилището има шаблон за pull request със същия списък. В описанието обяснете
**какво** се променя и **защо**. Ако поправя докладван проблем, напишете
`Fixes #123` — GitHub ще затвори issue-то при сливането.

## Правила за разработка

- **Следвайте съществуващата архитектура.** Първо прочетете
  [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — обяснява границите главен
  процес/renderer, картата на `handlers/*.js` и капана с реда на зареждане
  (TDZ), който лесно се пропуска при добавяне на нов модул.
- **Всеки IPC handler минава през помощната функция `run(fn)`** — хваща грешки и
  връща `{ok:false, error}`, никога не хвърля към renderer-а.
- **Нов домейн в `handlers/` следва модела:**
  `module.exports = function registerXHandlers(ipcMain, deps) { ... }`.
- **Без нови тежки зависимости**, когато вградените възможности на Node/Electron
  стигат — тестовата рамка е вграденият `node:test`, XLSX импортът е с вградения
  `zlib`, а не пакет. Всяка нова зависимост усложнява `npm run build` и
  подписването на инсталатора, а програмата се инсталира от библиотекари, които
  не могат да разнищват счупен инсталатор.
- **Пазете съвместимостта.** Базите в истинските библиотеки носят години записи.
  Промяна по схемата трябва да мигрира заварените данни, да не предполага празна
  база и никога да не пренаписва мълчаливо въведеното от библиотекаря.
- **Коментарите в кода са на български** — проектът обслужва българска библиотека
  и целият домейн (Наредба № 3, КДБФ, дневник) е българска регулаторна материя,
  която не се превежда добре.

## Обратна връзка от библиотека

Ако сте библиотекар или тестер и ползвате InvLib върху истински или пробен фонд,
ползвайте шаблона **Обратна връзка от библиотека / Library testing feedback**.

Пита кои части сте ползвали, какво работи добре, какво може да се подобри и къде
сте заседнали. Обратната връзка от работеща библиотека струва повече от всякакво
тестване от страна на разработчика. Какво работи добре е също толкова важно,
колкото какво не работи — то казва какво не бива да се счупи.

За въпроси и разговор, вместо доклад, ползвайте
[Discussions](https://github.com/plam4o4o-source/yavorec-katalog/discussions).

## Преглед на промените

`main` е защитеният, публикуван клон — от него излиза автоматичното обновяване на
вече инсталираните програми. Промени се разработват в отделен клон/PR и се
мерджват само след преглед и зелени тестове.

Какво гледа прегледът:

- **Вярност спрямо наредбата.** Число, което излиза на подписан документ, трябва
  да е вярно. Където правилото идва от Наредба № 3, кодът казва от кой член.
- **Тестът.** Пада ли, ако поправката се върне? Тест, който минава и в двата
  случая, не доказва нищо.
- **Безопасност на данните.** Заварени записи не се презаписват мълчаливо, а
  частичен провал не оставя базата наполовина променена.
- **Яснота за следващия.** Не находчивост — данните на библиотеката зависят от
  код, който и непознат да разбира след пет години.

Очаквайте въпроси. Те са към промяната, никога към човека.

## Общуване

Проектът има [правила за общуване](CODE_OF_CONDUCT.bg.md). С участието си се
очаква да ги спазвате.

Професионално, уважително и по същество. Приемайте, че отсрещният се опитва да
направи програмата по-добра за някоя библиотека.

Тук има повече библиотекари, отколкото програмисти. Въпрос, който изглежда
елементарен, не е досада — програмата съществува точно за тези хора, и ако е
трябвало да се пита, значи не е било достатъчно ясно.

Критиката е към кода, документа или решението. Никога към човека.
